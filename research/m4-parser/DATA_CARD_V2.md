# M4 contrastive data v2 — preparation, no trained result

The first run learned its development templates but filled missing fields and
confused similar exercise names on other wording. This revision adds paired,
label-first examples: an explicit report versus missing units/reps, future plans,
negation, uncertainty, questions, ambiguous RPE scope or an unlisted exercise.
Closely named exercises share a context and the selected exercise deliberately
differs from the mentioned one. Labels are not generated by a teacher model.

- Train: original 4,000 unchanged + 1,200 positive/negative pairs = **6,400**.
- Dev: original 500 + 120 new pairs = **740**. Used for diagnostics, never claims
  independent generalization.
- Challenge: **240** rows from 120 pairs with separate seeds and wording; no
  identical normalized sentence in train/dev, the old tests or the 150-case corpus.
- The old 500 test / 60 handwritten cases remain diagnostics; neither enters SFT.
- Prompts contain only exercise names and the sentence. Selected exercise, done
  sets, actual values and prescription targets are excluded. Evaluation files
  have no assistant answer; training targets match stored labels exactly.
- Full artifacts are regenerated under ignored `data/generated/v2`. The committed
  [manifest](data/v2-manifest.json) binds every file and the revised system prompt.

This is synthetic, templated data, not private user data or verified teacher
distillation. Fresh challenge wording is a compositional synthetic check, **not
independent human evaluation**; shared concepts and the same generator limit it.
The protocol must be fixed before its first model evaluation. Do not tune on
challenge outcomes or silently turn it into training data. A later failure gets
an explicit new protocol, not another attempt against the same gate.

The token audit on the original saved Qwen tokenizer found maximum 296 tokens
for train, 287 for dev (including answer and end marker); no truncation is needed
at the existing 512-token limit. Inputs alone: challenge max 156, old test 179,
handwritten 156. These counts do not measure device latency. A real CPU smoke
used eight new train/dev rows, batch 1 and two optimizer steps: 45.2 seconds,
dev loss 0.04864, adapter and merged weights exported successfully. It reused the
saved **v1 merged weights**, not the original base, in an isolated environment
(torch 2.8.0+cpu, transformers 5.20.1, peft 0.21.2). This checks the training path,
not fresh-base training or candidate quality. The bounded GPU runner is pending.

Generate: `node --import tsx research/m4-parser/scripts/build-v2.ts`.
Check: append `--check`. Tests verify original-data preservation, label schema,
positive numeric/unit consistency, missing-unit negatives, exact targets,
disjoint normalized text and answer-free evaluation input.

Before another GPU opening, freeze the complete run, hardware bounds and gates.
Include the old weights with the new prompt as a baseline so a prompt effect is
not mislabeled as a training gain. Quantization comparison must precede guards;
both safety and accepted-input coverage must pass before enabling native writes.
