# W3b 实施设计：只替换本次尚未开始的动作

状态：以下为事前设计，现已按此实施并完成本地验证，迁移/上线状态见 [实施验证记录](W3B_VERIFICATION.md)。依据 [第 3 周任务](WEEK3_CODEX_BRIEF.md) 和 `TodayStore` / IndexedDB 队列；新账号真实性修正已先独立交付。

## 为什么先缩小到尚未开始的动作

现有组记录用 `planExerciseId + setIndex` 定位，保存时从当前会话处方读取动作名。如果直接把同一个 ID 的名称改掉，另一个设备里尚未发送的旧请求可能被记成新动作。因此不能只做一个下拉框再覆盖名字。首版只允许替换该会话内完全没有任何记录的动作，已完成、跳过或撤销过的组都算有历史；其他动作已经完成的记录原样保留。

## 事务与身份

1. 用户选器械、看候选、确认预览，才产生不可变请求；仅改 `workout_sessions.prescription`，不更新 `training_plans`。长期变更仍走现有批准账本。
2. 替换分配新的会话动作 UUID；原计划动作 ID 和前后快照保存在变更回执。旧设备仍持有原 ID 的队列必须冲突，不能自动改写到新动作。界面历史和统计不反向重命名实际组。
3. 共用当前本人事务、RLS、用户串行锁和请求哈希；校验活跃会话、处方上下文版本、原动作、可用器械集合、目录版本和目标动作。UUID 相同且字节一致返回原回执；内容不同拒绝；事务中任一检查失败整笔不写。
4. 撤销是有独立 UUID 的补偿，保留原回执。仅当该变更仍是目标动作当前版本且新动作没有任何组记录时可补偿；补偿也使用一个全新的会话动作 ID，避免复用旧 ID 接受过期请求。失败显示原因，不删除后续实际记录。
5. 会话结束与替换使用同一事务边界；结束后不能替换。对新动作保存第一组与撤销的并发，必须一方成功、另一方按真实状态拒绝。

## 候选与实际值

- 动作目录和选择规则先独立定稿：约 60 项，中英文名称/明确别名、动作模式、部位、需要的全部器械、目录版本。复用现有资料前核实来源和许可；不把现有初学者演示目录直接当作完整替换关系。
- 用户选择本次可用器械；未知器械不能视为拥有。只从满足全部器械要求、匹配预设动作模式/部位的目录中筛选，稳定排序，展示可解释原因。未识别原动作或没有合格候选时明确显示无候选，不临时让模型猜一个。
- 保留目标组数/次数/RPE 的含义为处方，在确认卡明确展示；它们不进入实际值。新动作重量与实际 RPE 默认未知，不沿用原动作的重量，也不声称两个动作负重或训练效果等价。
- 本 PR 不自动处置伤痛、不重排长期计划、不做模型调用；未知动作与需要人工判断的情形留给用户自行安排。

## 与离线队列的接口

- 新增替换/补偿操作仍先事务落入同一账号 IndexedDB，再显示“待同步”；请求含固定候选、器械、目录版本和前后动作 ID。投影改变后，后续记录绑定新的动作 ID。
- 发送按原顺序。另一个设备抢先记录了原动作时，服务端拒绝替换，后续新动作记录一起暂停；显示本地和云端差异，用户明确放弃队列后恢复云端。不能自动跳过替换却继续提交其后记录。
- 服务端和浏览器投影需要逐步对比；目录版本不匹配、过期预览、切换账号、存储不可用仍沿用 fail-closed 边界。只承诺已加载且保持打开的页面，离线冷启动和真机验收仍单列。

## 实现顺序与验收门槛

1. 固定目录、过滤器、请求 schema 和纯投影；单测覆盖器械子集、未知/歧义名称、无候选、固定排序、空值以及不能替换有历史动作。
2. 独立增量迁移建立本人可读的变更回执，运行角色仍无 superuser/BYPASSRLS；实现原子替换/补偿。真实 PostgreSQL 验证重放、跨账号、版本冲突、失败回滚、保存与补偿并发；长期计划前后哈希相同。
3. 接入当前 UI 和 outbox。浏览器覆盖确认/取消、断网替换→新动作记录→补发、响应丢失重试、多标签、旧设备请求、补偿前后刷新、已有组阻止撤销、结束竞争以及语言切换。
4. 精确提交全检查通过后再迁移/部署；正式域名使用新合成账号走真实 Auth → API → 数据库并独立核对回执/事件/计划原样，最后清理。每次真实失败和修正单独记录，不提前填通过。
