# 计划自动使用健身记忆 · 2026-10-17

维护者要求训练与饮食计划自动参考已保存的目标、身体数据和动作重量，保留简洁页面及修改前确认。此前计划工具虽然可读取记忆，但未定义冲突优先级，记忆读取失败可能仍生成预览，且新测量或撤销不会令旧预览失效。

## 实现

- `fitness-facts.ts` 复用仅包含本人实际记录的 SQL 投影，排除撤销、跳过、作废和未来日期。体重、腰围、偏好分别取最新值；训练最多 20 个动作、饮食 6 个，每个最多 3 条实际报告，显式标注截断。
- `plan-personalization.ts` 明确本次要求 > 确认偏好 > 设置。部分偏好保留未涉及设置；伤病与饮食限制保留。事实带原日期，未知 reps/RPE 为 null，不把重量视为 PR，不根据少量组记录估算总训练量或消耗。
- `AgentStore.planContext` 在本人锁内统一读取。服务器创建 `planning_basis` 不可变事件及内容哈希；发布、批准、执行均复查。没有记忆快照时模型路径不发布提案。列表检查仅在同一锁定事务内复用查询，不跨请求缓存。
- 增量迁移仅增加计划角色的实际数据 SELECT 权限、本人 RLS 和语句级事务锁触发器。没有赋予模型或计划角色写实际记录的权限。计划应用过的回执不会被后续新测量作废。
- 页面保持原流程，只补充旧方案失效提示。计划生成不保存身体数据，临时目标覆盖不偷偷写回长期偏好。

## 已执行验证

- 单元测试：131 项通过（6 个 mjs + 125 个 tsx），新增优先级/缺失/日期/稳定哈希测试。
- 真实本地 PostgreSQL 产品回归：76 项通过，新增 10 项涵盖快照、撤销、并发记录、只读权限、账号隔离、重复执行及截断。初次并行启动两个依赖初始化的测试文件产生建表竞态，改为与 CI 一致的顺序执行后通过。
- 真实 DeepSeek + 本地 PostgreSQL 合成预检：4/4 完成。旧设置“减脂、每周 5 天”与确认记忆“增肌、每周 3 天”冲突时采用后者；计划使用 72.5 kg、卧推 50 kg 的原日期及无奶制品偏好；只改指定组数时其他天保持；临时维持目标不修改保存偏好。预检未应用任何计划，原实际记录数量保持不变。
- 上述四次完整调用分别为 7005、6237、2964、7575 ms；仅这四次合成调用，无浏览器/真实托管鉴权，不是生产 P95。模型在工具阶段返回方案，未记录普通聊天首字，不报告 0 ms 首字。
- 浏览器新增训练/饮食记忆场景。首轮饮食通过；训练断言错误地寻找已收进历史的失效预览，保留失败 trace，修正为从“查看回执”选择旧方案后验证不可应用。完整回归 81/82，剩余一项断言旧提示“已变化”，修正后定向通过；共 82 个场景已通过。
- WebKit 手机视口补测最终 4/4：当前计划、跨页流式历史、训练记忆与饮食记忆。首轮 3/4，训练测试在重载恢复前统计了 0 条历史，补充等待原消息恢复后通过。此处为桌面 WebKit 仿真，不是真实手机或微信内核。
- 最终构建、类型检查通过；lint 无错误，保留研究目录两条既有警告。[真实模型摘要与逐段耗时](evidence/plan-memory/real-model-preflight.json) 使用合成数据。
