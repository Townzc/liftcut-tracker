# 访客 AI 与确认记忆

## 使用流程

- 访客在 Agent 同意模型数据说明后，使用与账号相同的流式模型与受限工具循环。
- 身体、饮食、独立动作实际重量和健身偏好先显示草稿，点击确认才追加本机记录。
- 登录后核对待同步清单与目标账号，再确认导入。已确认记录进入账号事件账本；不覆盖账号设置或当前计划。
- 设置 → 记忆显示最新的已确认体重、腰围、各动作重量和偏好，以及各自原始日期。撤销先确认，再追加补偿事件。
- 询问两个月前的数据时按日期查询原始记录。最近六轮仅是模型对话上下文；新聊天、聊天删除不影响事实记录。

## 事实边界

体重和腰围分别选最新的非空测量值，不将一条缺少腰围的体重记录当成腰围清零。动作重量来自实际训练组、完成的旧动作记录或已确认的独立动作补录，不读取计划目标。缺失组数、次数、RPE 保持 null。动作按名称匹配，不猜测不同器械或动作变体等价；latest 不是 PR。

偏好只覆盖目标、训练安排、器械、饮食、身体注意事项与单位。模型必须引用当前用户原话，用户再确认；不从闲聊推断人格、疾病或个人属性。同类新偏好追加历史，撤销后更早的有效值可以恢复为最新值。未确认草稿不会进入事实记忆。

## 存储与权限

访客记录采用 localStorage 的独立 UUID 命令键。刷新、切页与新聊天不删除确认记录；无痕会话结束、浏览器清理或设备损坏仍可能丢失，长期保存需登录同步。访客聊天本身仍仅保留本次页面会话。

访客模型请求提交最多 500 条有效本机记录；超限或校验失败不静默截断。仅查询所需结果进入模型提示，字符串均视作不可信数据。账号请求拒绝客户端提供的访客事实，改由 owner/RLS 查询；访客无法读取账号表或计划账本。

访客导入冻结待确认清单和工作区 UUID。服务端将工作区认领与所有记录插入置于一个事务，按账号与内容哈希重放同一回执；跨账号、改内容和 ID 冲突会拒绝。丢失响应保留本机日志，重试不会创建第二份记录。收到且核对完整回执后只移除这一批记录，并保留同期新增记录。旧访客实际数据沿用稳定映射；未导入的旧计划和设置留在本机。

## 试用额度

服务端签名 HttpOnly / SameSite cookie 标识访客（30 天有效），不信任浏览器的计数器。私有 schema 只记录随机请求/访客 ID、每日加盐 HMAC 网络摘要和时间，不保留访客提示词或健康数据。

- 每位访客：UTC 每日最多 10 个模型请求，每分钟最多 6 个。
- 同一网络摘要：每天 40 个，每分钟 12 个；每日全站试用最多 500 个。
- 三种预算在同一短事务锁内预留，模型调用在事务外；重复请求 ID 拒绝重跑。
- 已预留的失败/取消请求也计数，防止失败重试绕过成本限制。达到限额仍能手动记录或登录使用账号额度。

## 验证与限制

单元测试覆盖字面引用、未知值、历史日期、撤销、浏览器存储与导入丢失响应。真实 PostgreSQL 测试覆盖额度并发、同网络换 cookie、事务回滚、重放和账号隔离。浏览器测试经过真实应用 API 和数据库，模型与认证使用明确的 HTTP 测试替身；它不代表真实模型或真实 Supabase Auth 的效果。正式站实际模型、认证和部署 SHA 的证据在发布交接中另存。

记忆列表最多返回 100 个最新指标，优先保留身体与偏好；多动作结果标明未全部返回，可用动作名定向查询。日期历史单次查询最多 92 天，历史保存没有这个时间上限。没有向量库，也不自动摄取其他对话。
