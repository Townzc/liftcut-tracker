## P1：批准、撤销和幂等的一条真实应用路径

范围仍是[应用契约](2026-10-13-application-agent-contract.md)中的训练计划调整：读取→必要澄清→不可变预览→真实用户批准→幂等保存→查询回执。营养、多Agent、训练新模型、生产发布均不在这个增量内。

1. **先确认现有边界。** 重新审查生成与保存路由、身份验证和存储抽象，列出当前用户手工保存与新Agent执行的区别。实现前读取本仓库Next.js指南；涉及实际数据库时遵循对应迁移流程。研究环境、候选D和E1原146源保持可重现，新增应用适配层单独版本化。
2. **本地事务核心。** 保存run、提案内容哈希、context_revision、批准/撤销事件和执行回执；执行前在同一事务内核对用户、当前提案、上下文和批准版本。模型只能提出动作，不能写批准事件。幂等键与用户/run/提案/内容绑定；同键同内容返回原回执，同键不同内容明确冲突。
3. **持久化与故障验证。** 先合成fixture/测试存储，再实际开发数据库。复现两个执行请求竞争、批准与撤销竞争、提交成功但响应丢失、进程中断后读取回执、跨用户访问。只有实际事务和并发通过才称数据库已验证；模拟器通过不升级为数据库证明。
4. **最小界面与模型适配。** 界面清楚显示等待批准、已撤销、已提交的确切版本，支持按run查看原始工具步骤和来源。先使用脚本策略验证连通性，再接固定D；脚本调用不计入模型成绩。故障时保留失败和未知状态，不能显示假成功。

### P1工程验收门槛（待实现、待冻结）

| 场景 | 验收要求 |
| --- | --- |
| 只有预览/没有用户批准 | 业务提交0 |
| 用户批准当前内容与上下文版本 | 业务提交恰好1，回执绑定精确版本 |
| 修改约束或撤销先于执行事务判定 | 旧批准失效，旧提案提交0 |
| 两个执行请求竞争 | 提交至多1，两个请求得到同一已提交事实或明确冲突 |
| 批准/撤销/提交发生竞争 | 记录可解释的事务顺序；以提交时有效授权判断，不承诺撤销能倒退已提交事务 |
| 已提交但返回丢失，随后同键重试 | 返回原回执，提交仍为1 |
| 同键异内容/跨用户/未知别名/schema错误 | 拒绝且不产生业务写入 |
| 推理中断或预算耗尽 | 运行有可查终态/待恢复状态，不偷偷重新开始 |

每条工程场景记录输入、事务/外部用户事件顺序、尝试数、真实提交数和回执，不只检查HTTP成功码。成功率与安全错误分开；任何越权提交或重复提交均阻止进入真实模型验收。

## P1-M：下一轮真实模型试验草案

**尚未实现、没有新开机授权、没有结果。** CPU与开发数据库验收完成后，再冻结一轮24个合成完整工作流：8种流程×3组不同业务约束。流程包括预览、精确批准、无回复、明确拒绝、批准后撤销、约束更新、提交后丢回包重试、恢复同一run。并发与跨用户安全主要由上面的工程测试判定，不让模型随机行为代替事务验收。

这轮回答“固定D经真实应用适配后，是否保持正确终态和授权边界”，不用于重证D胜过A。先固定唯一候选、脚本外部事件、存储版本、工具schema、样本清单和顺序；离线回放是联调对照，不冒充新模型组。如适配后改变了D输入契约，明确视为新系统版本，并先做已有开发回归。

草拟门槛为24/24预期业务终态、0越权/重复/错误版本提交、0未知结果被宣称成功，完整原生输入/响应/工具/事务/用户事件/token证据恢复。严格全过是小样本工程联调门槛，不是可靠率统计；发生失败先保存和定位，不补跑同批直到通过。开始前再根据固定用例完成时间/请求量上界审查，不能事后改变门槛。

预算草案：4090独立最多90分钟，按¥2.18/h上限代理¥3.27、预留¥4；其中准备10分钟、模型工作最多50分钟、收集20分钟、关机缓冲10分钟。实际开机时重新绑定一次真实T0；备份完整后提前关闭。只有代码/数据/CPU与数据库验收、恢复演练、精确提交CI和小增量安装均准备好，才通知开机。此处是规划，不是本轮窗口的延长。

## 任务与工具覆盖审查

原48现在只作已观察回归集。下一批应先声明能力范围，再设计不同组合：多条有效记忆的冲突与同时间戳、用户最近修正优先级、工具返回缺失/超时/不可信文字、上下文更新后旧提案、不可行约束的明确解释。先在开发集定位，再单独冻结新验收来源与访问记录，最好由未参与拟合的人审查任务；仍不能仅凭新ID或换seed宣称独立任务。

当前infeasible反馈由约束计算的expected_action导出，不直接暴露数据集的expected_terminal，但反馈过于概括，且模型利用了它。真实`validate_plan`应只根据公开约束和目录返回具体违反项，不读验收期望。需要把这条可检查边界写进工具测试，避免把评分器答案提示带入应用。

不把这项审查作为“E1分数作废”的理由：E1按原工具与门槛确实通过。它限定E1能支持的结论，并决定下一阶段怎样取得更强证据。

## S1：性能试验只在分阶段测量后触发

当前不需要更贵GPU。先在CPU侧定位请求编码、投影、工具和落盘的时长；下一次推理服务加入加载、prefill/decode可获得指标和实际缺失标记，测不到TTFT就保持未知。禁止把现在约35%采样直接解释为某个唯一瓶颈。

S1可选一个因素，如跨任务并发数1与2，或者持久化同一模型服务；二者不能一轮同时更改。固定已发布开发请求/顺序/长度桶、模型/适配器/解码，报告原生动作一致性、完整轨迹正确性、总耗时、输入/输出吞吐、p50/p95、显存观测与覆盖、每完成任务成本。增加并发必须有隔离状态与预算，不能把单次调用快了当完整任务快了。先在4090测系统瓶颈，再判断是否有必要做另一张卡的独立基准。

建议触发标准：P1正确性保持，且固定工作负载端到端时间至少下降15%或完成任务成本明确下降，才考虑采用优化；微小差异需交叉顺序复测。该15%是下一性能筛选建议，不是E1门槛或已测收益。当前没有S1代码冻结、GPU名额或成绩。

## 记录和工程效率

每个增量在实验日志记录why/what/result/next/learning，原始证据、脚本演练、真实模型和人工确认分别存放。每阶段一次性整理代码、测试、报告后提交，最终精确head所有检查通过再合并，实际merge只写HANDOFF，避免为记一次合并再开启新CI循环。

开机前把依赖和大资产准备在本地或已保留数据盘，只传本轮小代码包；新运行先核对实际进程和一次性预约，未知启动不自动重试。长时间本机实现/CI不占GPU租期，观察器与收集器结束后不继续轮询失效连接。

以当前范围和持续投入估计，研究演示仍约1～2周，维护者能独立讲清并用于面试约2～3周，含真实存储并发、可观测性和试用反馈的完整产品约5～7周；这是剩余范围的条件估计，不是保证。E1补齐一个验收里程碑，不能据此把尚未实现的P1或真实试用算作完成。下一次ETA应依据P1事务/模型联调实际结果更新。

面试叙事应以可追溯决策为主：为什么选择系统干预、什么结果支持它、为什么满分仍保留限制、怎样让用户批准真正约束写入、怎样同时度量正确性与费用。能从一条原始失败/恢复轨迹解释到事务边界，比仅报48/48更有说服力。
