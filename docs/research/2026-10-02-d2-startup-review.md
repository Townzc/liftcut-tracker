# D2 启动失败复盘与修复

本轮开机没有启动 D2 控制器、训练或模型推理。失败发生在本地依赖选择和文件上传，
不是模型能力下降。原始观测见[证据目录](../../research/liftcut-agent/reports/d2-startup-failure-2026-10-02/observations.json)。
原 seed42 四份权重、80 例/组、320 例总分母、544 次生成上限和 G1 门槛均未改变；
48 个保留任务仍未使用。

主要责任在启动实现：事前完整 CPU 演练覆盖了执行和恢复，却没有覆盖操作者最终使用的
传输入口；预检与传输 Python 未隔离；恢复代码重复上传；上传循环也没有按更早的
10 分钟启动截止停止。原 120 分钟保护不能代替“实验未开始时尽早结束租用”。
网络吞吐慢是这次观察到的条件，不足以单独解释上述实现缺口。

## 已做的修复

- 新增版本管理的 [launch_d2_remote.py](../../research/liftcut-agent/launch_d2_remote.py)：
  传输进程仅使用 Paramiko；tokenizer 预检与恢复调用配置中已有的独立 pinned Python。
  默认只有离线预检；实际执行必须显式提供新 opening ID、真实开机代理和 `--execute`。
- 每个远端部分文件先计算 SHA256，与本地同长度前缀匹配才追加缺失后缀。完整文件
  复用前也核验哈希；不匹配、超长或软链接立即停止并保留原件。关闭写入后再次核验
  全文件长度与哈希。进度中的 queued bytes 不表示服务端已确认落盘。
- 新增独立 [d2_prelaunch_guard.py](../../research/liftcut-agent/d2_prelaunch_guard.py)：
  在大文件上传前启动，原开机 10 分钟内没有绑定正确来源与截止时间的控制器 opening，
  就请求关机。使用单调时钟防止本地时间回拨延长窗口；畸形 opening 不取消保护。
  它补充原 90/120 分钟执行限制，不改冻结 GPU 代码，也不凭 opening 声称模型已运行。
- 在传输前检查历史环境版本、4090、模型/adapter 文件存在和剩余磁盘；不安装包、
  不扩盘。版本核验不代替模型文件和真实权重的完整检查，后者仍由冻结控制器执行。
- 同一个 SSH 连接完成上传、单次控制器派发与原有收集器。派发意图先落盘；异常后
  不自动重连、重复启动或重置预算。每次新开机使用新的 ops/run 和本地恢复目录。

云端执行提交仍是 **06654db287a5d51c4aad6bf57fcee40d21555afc**（PR28 已检查提交）。
这次新增的本地入口和额外启动保护分别保存来源哈希，不混充为原 GPU 源码的一部分。
旧 R1 的 f18 提交及所有科学评测条件也保持不变。

## 验证与证据边界

18 项新增 CPU 检查覆盖前缀续传、完整复用、损坏拒绝、写入关闭异常、原期限、
畸形/错误/迟到 opening、单调时钟、新目录隔离、独立 Python 和原始成本代理复算。
完整入口测试使用明确标记的模拟 SSH/SFTP、模拟控制器和收集器，编译所有远端命令；
这不是一次真实服务器部署。平台关机命令在测试中由 stub 替代。

真实本地离线预检则使用本次出错的同一传输 Python，成功调用独立 tokenizer 环境，
重新检查 8 个原 seed42 adapter 文件（528,755,732 字节）、tokenizer 和冻结来源。
本机最终全量 456 项回归通过（160.914 秒），冻结执行来源与真实 adapter 字节复验通过。
最终精确提交 CI 的结果记录在交付 PR；GPU 端的新入口仍待下次真实开机验证。
PR28 已有的 320 次 CPU oracle 演练没有被记成新 D2 模型结果。
