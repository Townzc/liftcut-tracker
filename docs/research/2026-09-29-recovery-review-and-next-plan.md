# Recovery 实验复盘与下一轮设计

状态：**复盘已用 CPU 重算；下一轮仍是设计，尚未生成或冻结数据，也没有新的模型结果。现在不需要开服务器。**

本轮的核心判断是：训练、回放和备份链路已经跑通，但还没有证据证明 recovery SFT 带来收益。接下来最有价值的工作是建立可信的恢复能力对照实验。扩大模型、增加训练轮数或直接上 DPO/RL，都无法回答当前失败的原因。

本文细化并替代[上一份结果报告](2026-09-29-recovery-results.md)末尾的临时“40 train / 8 dev / 24 test、立即三组评测”方案。历史数据、评分和实验日志保持原样。技术路线仍以 [roadmap](../AGENT_RESEARCH_ROADMAP.md) 为准。

## 1. 可以确定什么

现有两个 adapter 均从同一个已指令微调的 Qwen3-4B-Instruct-2507 开始训练，单个 seed，38 次优化更新，12,758 个监督 token。不是从预训练模型开始。原始数据的可见 ID 包含类别提示；后续 opaque-ID 探针只改了 ID，使用原 adapter、重复任务，没有纠正训练污染。

| 同一组 24 个 opaque-ID 诊断任务 | 未做项目 SFT | 普通 SFT | 混合恢复 SFT |
| --- | ---: | ---: | ---: |
| 成功数 | 1 | 20 | 17 |
| 请求数 | 111 | 147 | 166 |
| 无效 `validate_plan` 返回数 | 36 | 7 | 33 |
| 同一 episode 内重复提交相同无效 plan 的额外次数 | 13 | 0 | 26 |

普通 SFT 与混合 SFT 的三个差异都发生在等待确认：普通成功、混合错误结束为 `previewed`。没有混合独有成功。两者共同失败的四个任务是三个“记忆更新 + 缺少时长”和一个记忆更新任务。

这些数值支持“本次配置没有观察到 recovery 优势”。它们不支持“recovery 方法无效”，也不能作为独立测试集上的泛化成绩。每个类别只有 3 个相关 bundle 实例，不能把多次请求当作独立样本来扩大样本量。

此次新增 [CPU 复盘报告](../../research/liftcut-agent/reports/recovery-forensics-2026-09-29.json)先验证旧训练日志和两套 rollout，再逐项计算覆盖率和失败诊断。144 个 episode 全部回放；没有新增 GPU、API 调用或权重验证。上轮已完成的真实权重备份验证是另一项历史证据。

## 2. 深挖后新增的发现

### 2.1 “恢复训练”覆盖的错误与实际失败不匹配

24 条恢复示范只注入了两类错误：

| 注入错误 | 次数 | 对应后续行为 |
| --- | ---: | --- |
| `unnecessary_clarification` | 15 | 已知字段不再追问，或只追问真正缺失的字段 |
| `approval_required` | 9 | 未获批准或已被拒绝/撤销时正确结束 |
| `validate_plan` 返回 `valid:false` | **0** | 没有相应恢复示范 |

混合训练的 300 个决策中，150 个来自 recovery 版本，但只有 **75 个输入历史真正改变**，只有 **24 个紧接着错误返回**。150/300 不是“50% 的决策都在学习立即纠错”。其余改变的历史是错误之后的后续正常步骤。

旧评测全部从 reset 开始；48 个原始 fixture 的 `faults` 全为空。模型可能自己走入错误状态，但不同模型遇到的错误不相同。因此旧评测能比较整体行为，不能单独比较“面对相同错误历史，谁更会恢复”。

### 2.2 澄清样例既少，又与记忆更新绑定

150 个独立正确决策中只有 3 个 `request_clarification`，全部询问 `max_minutes`；只有 75/6,379 个目标 token 属于澄清，约 1.18%。另外，`validate_plan` 和 `propose_plan` 合计占 3,981/6,379 个目标 token，约 62.41%。这是标签分布，不是测得的梯度贡献。

三个缺字段训练任务全部包含器械记忆更新；没有“单独缺信息”，也没有“追问后用户不回答”。原来的 `partial_clarification` 名字容易让人以为覆盖了部分答复，实际只有一个缺失字段，且 fixture 会给出完整答案。

普通 SFT 在 opaque 诊断的三个此类任务中确实调用了澄清工具，但全部询问不存在的 `action` 字段，**有效澄清数为 0**。不能用“调用过澄清工具”代表会补齐信息。

### 2.3 ID 探针还暴露了被总分掩盖的记忆退化

当前 `grade()` 在必要信息未补齐时先返回 `wrong_action`，不继续检查器械。为诊断而把 fixture 的时长答案仅补给离线评分器，再检查模型已经提交的第一个 plan：

| SFT 第一份 plan | 原始含提示 ID | opaque ID |
| --- | --- | --- |
| 普通 SFT，3 个组合任务 | 补齐时长后 3/3 合法 | 2/3 仍违反器械约束 |
| 混合 SFT，3 个组合任务 | 补齐时长后 3/3 合法 | 1/3 仍违反器械约束 |

这只是**固定 plan 的评分器反事实检查**。没有让模型重新接收答案或重新规划，不代表模型获得答案后会怎样表现。真实任务仍然全部失败，原评分没有变化。

它说明“都失败了，所以行为没有变”不成立。读取了 `get_memories` 也不代表使用了正确记忆。后续应分别测无记忆/有记忆、完整信息/缺信息的四种组合。

### 2.4 记忆任务还有位置捷径

六个训练记忆任务全部把最高 revision 放在最后，全部 confirmed、没有过期条目，也没有用户在 preview 后修改约束。旧/current 名称与位置一起提示了新旧关系。

opaque 探针同时去掉类别词和 `old/current`，改变 tokenization、衍生 proposal ID；不能把分差单独归因为类别泄漏或某个记忆能力。下一版必须打乱条目顺序、按明确 revision/confirmation/expiry 规则判定，先用 CPU 对抗变体验证契约。

### 2.5 现有评分只证明较窄的事情

- `valid:false` 是成功返回的工具结果，所以不会进入 `tool_errors`。混合模型在两个组合任务上产生了大量无效验证，其中 26 次重复完全相同的无效 plan。工具异常少不等于恢复成功。
- `clean_completion` 保留其旧定义。新增“无无效规划的完成率”必须另起指标，不能重写历史定义。
- 当前 evidence 检查允许只引用一个原始 record，即使计划实际依赖更新后的 memory。CPU 反例已验证。因此不能声称已经验证“引用了所用最新记忆”或语义证据忠实性。
- full-scenario digest 生成 proposal ID。只改变隐藏的 approve/pending 行为，初始输入和读取结果不变，proposal ID 却会改变。哈希本身不证明模型能解码未来结果，但破坏了严格相同前缀的对照。
- 未适配模型的低分混有原生调用格式失败和输出截断。不能把 1/24 全解释为规划能力差。

## 3. 下一轮要回答的具体问题

| 问题 | 目前证据 | 下一步鉴别方式 |
| --- | --- | --- |
| 相同错误之后，recovery SFT 能否改善后续决策？ | 旧实验没有受控错误起点 | 两个新 adapter 从完全相同的固定错误前缀继续，报告第一步和最终状态 |
| 改善是否牺牲正常流程，特别是等待确认？ | opaque 下混合组额外失败 3 个 pending | 同时保留从 reset 开始的正常任务；等待确认作为单独阻断项 |
| 是缺信息、记忆选择，还是组合任务导致失败？ | 两因素在旧澄清训练中完全绑定 | 训练和开发评测都包含四种组合，并检查最早偏离正确状态的决策 |
| 模型是否依赖名字/条目顺序？ | opaque 下发现额外记忆错误 | CPU 先保证语义不随 ID/顺序变化；模型稳健性探针单列后续开发实验 |
| 稀少短动作是否被 token 平均目标压低？ | 澄清标签占比约 1.18%，只是线索 | 若新 clean 仍失败，先做固定前缀决策诊断，再单独比较损失加权；首轮不同时改变权重 |

保持“修正数据”与“改善模型”两种结论分开。新旧数据、样例覆盖一起变化之后，新旧分数不能用来估计单一改动的因果收益。下一轮最主要的可解释比较是**同一新数据版本内，普通 SFT 对混合恢复 SFT**。

## 4. 分阶段执行方案

### 阶段 A：CPU 准备，不租 GPU

设计目标是 **4 个训练 bundle × 12 类 = 48 个训练任务；1 个开发 bundle × 12 类 = 12 个开发任务**。另外预留 **4 个新测试 bundle × 12 类 = 48 个测试任务**，第一轮 GPU 不评测它们。以下数量尚未生成、冻结、分词或验证。

每个 bundle 覆盖：

| # | 条件 | 预期关键行为 |
| --- | --- | --- |
| 1 | 完整约束、仅预览 | 合法 preview，无写入 |
| 2 | 应用意图、明确批准 | 当前 proposal 正好写入一次 |
| 3 | 应用意图、没有批准消息 | `awaiting_user` |
| 4 | 用户拒绝 | `declined`，无写入 |
| 5 | 先批准后撤销 | `declined`，无写入 |
| 6 | 信息完整但不可行 | 有依据地 `infeasible` |
| 7 | 只缺时长，有回复 | 先问时长，再规划 |
| 8 | 只缺时长，无回复 | 先追问，再 `awaiting_user` |
| 9 | 只缺器械，有回复 | 先问器械，再规划 |
| 10 | 只缺可用日期，有回复 | 先问日期，再规划 |
| 11 | 完整约束、记忆覆盖旧器械 | 使用有效最高 revision |
| 12 | 记忆覆盖 + 缺时长，有回复 | 同时正确处理两个因素 |

这会提供至少 20 个不同澄清上下文，覆盖 3 个缺失字段和不回复情况，而不是只重复原来的 3 个示范。完整/缺时长 × 无记忆/有记忆的四格由 1、7、11、12 实现，其他约束尽量匹配。仍不代表覆盖所有字段或真实用户分布。

数据与审查要求：

1. ID 从独立、固定的标识种子生成，不包含类别、终态或 split。批准/拒绝/等待/撤销反事实共享相同可见 records 和事件前上下文；新的 rollout 身份也不能取决于隐藏标签。完整 scenario hash 只留在 harness 审计中。proposal 的授权仍绑定当前 episode 状态，不能因为复用对照 ID 放宽写入检查。
2. 同一 bundle 和其反事实、顺序变体留在同一个 split。分词前检查模型可见的每条消息，不能只扫描顶层 metadata。测试数据仅用于标签可实现性、契约测试和封存，不生成训练目标。
3. 两个记忆条件中的条目顺序配平；确认、有效期和 revision 的对抗检查必须能区分错误规则。训练/开发适度覆盖过期或未确认的高 revision 干扰项，具体组合写入 manifest，不能靠固定位置解题。
4. CPU 回放全部正目标，拒绝 invalid target。训练错误只作为历史，不能进入正标签。两组逐位置的正确目标必须 token 完全相同，明确列出实际改变的历史与立即纠错的决策数。
5. 对新数据重做 tokenizer/mask、最长输入、每类动作与 target-token 分布、两次独立目录重现。旧的 12,758 token 不是新预算。
6. 加入评分器变异检查：错误器械、漏问字段、假批准、错误终态、过期记忆不得获得对应新指标；合法替代计划也应通过。第一轮保留旧 task-success 契约，新增分析指标独立版本化。若要修改工具提示或评分语义，必须在冻结前单列版本，全组统一使用。
7. 固定工作流必须通过；但其 100% 只证明任务契约可实现，不是模型结果。人工可读导出至少覆盖所有行为类型和三个错误类型，复杂记忆/澄清组合逐条检查。

本阶段交付：新数据/分组 manifest、泄漏与前缀不变性测试、训练 decisions 与 token 报告、固定恢复前缀、评分说明、不可变运行配置和实际预算估计。完成这些后才能把状态改为“可开机”。

### 阶段 B：一次开发诊断窗口

| 组别 | 数据/训练 | 用途 |
| --- | --- | --- |
| U | 同一未适配指令模型 | 观察协议与任务起点，不能单独归因为推理能力 |
| C | 新版正确轨迹 SFT | 普通 SFT 基线 |
| R | 同一批正确目标，配对混入错误历史 | 估计恢复上下文的作用 |

沿用 pinned 模型/revision、NF4/BF16、LoRA r16/alpha32/dropout0、lr 2e-4、2 epochs、seed42、累积8、每步按监督 token 平均。采用最终 adapter；不按测试分选择 checkpoint。C/R 的顺序、每步目标、监督 token 和步数相同，额外输入 token、GPU 时间另报，不声称总算力匹配。第一轮不同时调整损失权重、学习率、提示词或解析修复。

R 的注入配方在看新模型输出前冻结：保留“多问已知字段”和“无批准写入”，新增“缺字段时先提交 plan，收到无效验证，再正确澄清”。三种错误按适用状态分配，不能对所有场景机械注入相同动作，也不能用隐藏答案构造 policy 历史。

评测分成两个独立面板：

- **正常流程：** U/C/R 各跑 12 个开发任务，共 36 个完整 episode，保持现有每次 512 output tokens、4096 context、greedy、最多 24 个环境步骤。
- **固定错误状态续跑：** 三类错误各 3 个预先审核的开发前缀，共 9 个起点，每组都接收逐 token 相同的起点，共 27 条续跑。E1 使用 preview/approved/memory 三个父任务中的已知字段误问；E2 使用缺时长/器械/日期三个父任务中的无效规划；E3 使用 pending/declined/revoked 三个父任务中的被拦截写入。前缀由 harness 重放，assistant/tool/user 顺序保持真实，不能把参考正确下一步塞进输入。当前 user-simulator 状态、proposal 和撤销状态必须一并恢复。

合计 **63 条模型轨迹**，不读取测试分数。续跑只能消费原任务剩余的环境步数；每个前缀至少预留 8 步，否则在 CPU 阶段拒绝该前缀。同时报告第一步是否属于合法恢复动作集合，以及剩余预算内的最终任务成功。第一步可接受动作要按状态预注册，允许必要的重新读取，不能仅以与脚本字面完全相同作为唯一答案。

注入前缀里的错误由 harness 造成，单独计数；模型续跑产生的错误另计。尤其不能把前缀中注入的 `apply_plan` 误报为该模型自主越权。使用匹配的无错误前缀做语义/状态 CPU 对照；首轮模型的恢复面板明确是条件恢复能力，不与 reset 面板混成一个成功率。

所有比较固定同一工具/提示/解析器版本，保存原始生成。相同前缀可以保证组间起点相同；后续自由生成的历史可以分叉。现有 runner 尚不支持这套受控续跑审计，必须先实现、验证，不能只设置一个 flag 就宣称完成。

### 阶段 C：按开发结果决定后续，测试集先保持封存

首轮是小样本去留判断，没有统计显著性承诺。用以下预先确定的工程门槛，避免看完结果再改变成功标准：

| 开发结果 | 决策 |
| --- | --- |
| C/R 任一组仍有超过 2/12 个正常任务因格式失败而未进入有效任务决策 | 先隔离序列化/接口问题；若变更提示或解析器，单列新版本，所有组统一重跑开发对照 |
| C 在 7/9/10 三个单独缺字段任务中，至少 2 个未在规划前有效澄清 | 暂停扩大 recovery 训练；做固定正常前缀的下一步诊断，区分动作选择与长流程问题，再单独比较损失加权。12 的组合任务单列 |
| C 通过 11 而在 12 失败，且单独澄清较好 | 优先补组合覆盖，避免用重复简单任务掩盖问题 |
| R 比 C 在 9 个恢复起点上净多成功至少 2 个，覆盖至少 2 类错误；12 个正常任务最多净损失 1 个；pending 不回退；没有新增模型自主 blocked-write attempt | 仅视为值得复验的开发信号，进入重复 seed；不是论文式显著结论 |
| 只减少异常/重复调用，没有改善任务成功 | 记录为行为或效率变化，不称为恢复能力提升 |
| 任何真实未授权写入、回放不一致、未知数据/模型版本 | 该轮不能通过质量门槛，保留失败证据，先修正根因 |
| R 仍然没有优势，或等待确认继续回退 | 停止扩大这套配方；检查错误类型与采样分布。仍无信号则将负结果归档，把下一项研究改为澄清/记忆决策覆盖 |

出现信号后，固定方案补两个预先指定训练 seed（43、44），先看开发稳定性；若修改配置，则重新登记。最终候选固定后，才统一评测 48 个冻结测试任务，全部结果计入分母并按 bundle、类别报告；同一任务的反事实不是独立样本。4 个测试 bundle 仍不足以支持稳定的泛化区间，应把跨 seed/跨 bundle 分布完整列出。

只有后续任务分布/独立来源验证补齐后，才考虑把“对合成任务有效”扩大为更一般的 Agent 能力。外部 benchmark 的许可证、子集、协议、费用另做方案；多模态和 DPO/RL 不混入这次实验。

## 5. 指标与结果表应长什么样

主指标是 C/R **配对的任务成功数**，正常面板与恢复面板分开。并排报告 both-pass、C-only、R-only、both-fail，列出全部失败轨迹。

附带诊断必须包括：有效澄清/多问已知字段/缺信息却判不可行、当前有效记忆约束满足率、pending 终态正确率、第一步恢复动作、无效验证次数、相同无效 plan 重复次数、模型自主 blocked-write attempts、实际 writes、协议失败/截断/预算耗尽、请求/输入输出 token/耗时。

对恢复面板，固定前缀成本与模型续跑成本分开；对全流程，所有失败请求都计费计时。显式报告没有走到某项决策的数量，不能因格式失败把样例从主指标分母删除。额外证据引用指标只检查声明的机械契约；不称为自然语言语义忠实性。

## 6. 服务器、时间与预算

仍用已有 **RTX 4090 24GB**，用户提供的报价 **¥2.18/小时**；不需要 A800，不计划扩盘，不调用付费 API。下一轮不需要重新下载已有固定模型；若迁移后模型缓存或环境缺失，先修订启动时间估计。

**建议上限仍为开机起 2 小时，计算费按报价为 ¥4.36；总规划预留 ¥10。** ¥10 是包含未知存储费用的规划预留，不能代替供应商账单硬上限。超出已知配置、扩盘或提升机型时另报实际方案。

按已测日志作粗估，而不是运行承诺：

| 项目 | 估计分钟 | 依据/不确定性 |
| --- | ---: | --- |
| 环境、Git、完整性检查及模型加载 | 12 | 缓存仍在的前提 |
| C/R 训练 | 26 | 上轮两组共 12.8 分钟，场景数翻倍的近似；最终按 CPU token 数和最长序列调整 |

| 合计 | **120** | 各项只是排程，硬截止优先 |

固定 **开机第 90 分钟停止计算，最后 30 分钟用于备份/校验/关机**。预算估计需在开机前依据新 token 报告重新计算，达到或超出 90 分钟工作预算则先缩小、重新冻结范围或提出新预算，不能启动后延长截止。中途失败按失败保存并关机；不临时追加调参重跑。

若任一组因截止、OOM 或其他故障未跑全，发布为不完整运行，保留未完成项与失败原因；不能删除缺失样例或将已完成部分冒充三组完整比较。

运行管理继续使用不可变 Git commit、独立模型缓存、adapter/data/日志 manifest、本地校验后的备份回执和自动关机。先小后大分层传输，避免所有产物集中到最后才开始下载；中间 checkpoint 可作为可恢复权重保存，但没有优化器/RNG 状态就不能称为可精确续训。能取得供应商状态/账单才确认停止计费，SSH 不通只作为观察证据。
