## 首版必须回答的六个问题

1. **问题是什么？** 给出约束变化、过期记忆和授权变化导致的真实失败轨迹，说明
   固定工作流的适用范围，以及哪些状态组合需要模型判断。
2. **评测可信吗？** 解释 split/group、ID 泄漏审计、失败分母、状态评分、独立复现，
   区分脚本契约验证、开发诊断、保留测试和外部迁移四种证据。
3. **改进来自哪里？** 用单因素比较区分训练数据、提示词、显式状态表示及运行时
   检查。运行时拦截保障写入契约，但不能宣称模型没有尝试越权。
4. **改善是否稳定？** 报告相同案例上的进退、多 seed 的变化及类别失败。相关
   模板变体不能按独立用户样本估计置信区间。没有重复证据就保留 single-seed 限定。
5. **代价是多少？** 同时给出监督 token、输入 token、更新数、请求次数、实际生成
   与本地拒绝数、时间及费用估算；账单和预算预留分开说明。
6. **别人能否检查？** 冻结代码/data/config，提供 CPU 回放、原始轨迹和最小训练
   指令。演示同时展示成功、拒绝或等待、可解释失败，避免只挑最漂亮的一次。

## 独立验证的范围

48 个保留任务来自四个同作者 bundle 和共享模板，只能支撑有限的分组保留评测。
仍需增加不同任务来源的验证。优先评估现有工具调用 benchmark 的小型固定子集，
单列 adapter 前后的迁移/退化，不与本项目成功率合并。执行前才确定版本、许可、
任务清单、协议适配和预算；当前尚未下载或运行任何外部任务。

外部环境必须固定 commit 和评分版本。例如 τ-bench 官方仓库已说明部分任务的
评分修订会改变可比性，也包含不同交互模式；因此不能只写“使用最新版 τ-bench”
作为复现条件。[官方仓库与版本说明](https://github.com/sierra-research/tau2-bench)

若外部接口适配明显超出首版时间，先发布已验证的内部结果，明确外部验证未完成；
另行构造和人工审查新模板可以增强证据，但不能冒充外部 benchmark。

## 发布后的扩展

优先基于诊断选择一项：经过同一状态分叉执行审计的 DPO，或有可靠奖励与费用
测量的在线 Agent RL。视觉分支单独设计数据与评测。加入其中一项且取得可信对照
通常需要再预留数周，当前不承诺时间或效果，不占用首版必需的验证资源。
