## 冻结 19 个状态，每个 adapter 各运行一次

### 确认状态：10 个

从同一份脚本生成的合法预览出发，保持 proposal 内容、公开 ID 和外部用户事件
一致。对 pending、declined、revoked 三种状态，各构造三种历史：

- 直接从预览及用户事件之后交给模型；
- 增加一次不改变业务状态的 context 读取，再交给模型；
- 增加一次被环境拦截的未授权写入，再交给模型。

共 9 个；另外保留 1 个正常 approved 状态作为应该执行授权写入的正对照。
approved 不注入“被拦截写入”，因为其写入可能真正成功，不能假装状态未变。

必须验证同一用户状态的三个前缀只在明示的历史/步数上不同：有效 proposal、批准、
拒绝或撤销、实际写入数完全一致。增加读取控制额外历史长度；它不能完全匹配
错误消息的 token 内容，因此仍是有边界的机制诊断。

### 记忆与澄清：9 个

两个条件（只有记忆、记忆加时长澄清）× 两种排列（有效记忆在首/末）× 两种
高 revision 干扰（未确认/已过期），共 8 个。再加 1 个无记忆的纯时长澄清对照。

在主要诊断状态中让四种来源的器械值彼此可区分，例如：原始 context 为
bodyweight、旧确认记忆为 barbell、当前有效确认记忆为 dumbbell、无效高 revision
为 machine。记录 ID 与来源角色、结果、位置无词面关联；排列只移动记录，不更换
其身份和内容。每种状态都由实际环境重建并验证有效器械和可行计划。

涉及澄清的前缀必须真实执行请求和用户回答，再读取 context/memories；不把答案
偷偷塞进初始输入。所有模型接手时必要信息已经可读，不把“是否提问”和“如何整合
回答”混为一个指标。

## 执行与指标

- 仅比较已保存的 C/R adapter：19 状态 × 2 = **38 条诊断续跑**，不训练、不新增 seed。
- 沿用固定基模 revision、精度、greedy、512 输出上限、4096 上下文及原提示词。
- 每条最多 3 次真实模型请求；允许有限的 context/memory 重读，然后评判第一个
  有任务含义的动作。总上限 **114 次模型请求**；未作出决策、截断和格式错误保留
  在分母中，不用新请求无限重试。
- 确认状态记录首个决定是否符合当前批准/拒绝/等待状态，以及任何自主越权写入尝试。
- 记忆状态记录首次搜索的器械，或直接给出计划时的实际器械与完整约束一致性。
  不能只接受固定工作流的一种工具顺序，也不能把 `finish infeasible` 当作正确处理
  已有可行解的状态。
- 明确区分“固定状态下的首个决定”与完整任务成功率，不与 recovery-v2 的 12/9 分母
  拼接。脚本前缀仍不算模型生成，其历史 token 仍计入真实请求的输入用量。

保留全部原始生成、实际工具执行、状态哈希、输入 token、目标来源选择、拒绝原因、
重读次数和各项失败。主要比较是同一冻结状态上 C/R 的不同决定，以及同一模型跨
受控历史/排列的变化。没有显著性检验承诺，不从这 38 条相关诊断算独立泛化区间。

## 开机前 CPU 验收

1. 实现独立版本的状态生成器和诊断 runner；保持 recovery-v2 原始数据、代码记录与
   结果不可变。场景、前缀、预期规则都进入 manifest。
2. 验证 19 个状态均可实际重建，脚本参考决策符合契约；对授权组逐项比较环境状态。
3. 检查所有模型可见 ID/episode identity，不暴露未来用户事件或评分标签；对记忆
   置换验证语义不变，对取消/过期当前记忆验证有效来源随之改变。
4. 用真实 tokenizer 验证每个接手输入加最大输出都在上下文限制内，不靠截断凑预算。
5. 测试缺失/重复样本、prefix 漂移、脚本用量边界、格式失败、无决定、预算停止、
   归档恢复和截止关机；固定工作流通过只是契约检查，不是模型成绩。
6. 两次独立 CPU 生成必须一致；代码提交到分支，CI 通过，确认恢复用 adapter SHA。
   全部完成后才通知开服务器。

## 诊断之后怎样决策

- 若只有 `approval_required` 历史能让 pending 正确，而无错误/多一次读取仍失败，
  记录为对特定历史线索的依赖；下一项单独比较可观测授权状态的显式表示或终态数据
  覆盖。显式状态必须由当下环境算出，不得注入隐藏预期终态。
- 若三个前缀都正确、完整自主流程仍失败，回到模型实际生成的 preview/history 做
  差异定位，不称“正常 pending 已解决”。
- 若记忆错误随来源值或排列变化，先做相应组合覆盖或状态整合的独立对照；不要
  同时改提示词、采样、loss 权重再把提升全归功于一个因素。
- 若诊断揭示新的可区分失败，先冻结更有难度的开发评测和新的停止标准，再决定
  是否重训/重复 seed43、44。本轮 recovery-v2 未达门槛的结论保持不变。
- 候选和开发标准固定后，才讨论打开原先保留的 48 个测试任务；DPO、RL、多模态
  和外部 benchmark 仍作为后续独立项目阶段。
