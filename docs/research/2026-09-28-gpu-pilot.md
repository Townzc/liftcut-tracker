## 数据和训练实测

服务器重新执行了 CPU tokenizer 审计，结果与已提交报告完全相同：59 条决策，
104,177 个上下文 tokens、2,766 个助手目标 tokens，最长 2,973，无截断。
loss 仅监督最后一个助手决策，先前助手消息和工具结果都作为上下文。

配置：NF4 4-bit、double quantization、BF16 计算、LoRA all-linear r=16 / alpha=32、
dropout=0、micro-batch=1、累积 8、AdamW lr=2e-4、seed=42、gradient checkpointing。
每个 optimizer step 按目标 token 数加权，避免把长度不同的 micro-batch 等权平均。

| 实测项 | 结果 |
| --- | --- |
| optimizer steps | 20 |
| 实际处理决策 | 160（重复采样 59 条数据） |
| 处理输入 / 目标 tokens | 289,613 / 7,451 |
| 训练时间（含检查点保存） | 218.47 秒 |
| 输入 / 目标吞吐 | 1,325.64 / 34.11 tokens/s |
| 第一步 / 最后一步 loss | 0.17874277 / 0.00370713 |
| loss / 梯度 | 全部有限，无 NaN/Inf |
| 发生更新的 adapter tensors | 504 |

allocated 和 reserved 含义不同；后者包含缓存，不能把它等同于模型实际占用。
当前最长样本是 2,973 tokens，尚未测满 4,096 的训练峰值。数据反复使用且很小，
loss 快速下降只说明优化器能学习这批目标，不说明泛化或可靠性改善。

每 5 步保存 adapter、optimizer 与随机状态；最终检查点另行备份回本机，权重不进入
Git。当前保存了训练状态，但尚未实现并验证自动断点续训。

## 解析器问题与分开的诊断

原试跑固定选择 interactive-002 和 interactive-008，原转换器要求纯工具文本。
训练前为 0/2，训练后为 2/2，两轮轨迹均可回放。这个变化不能作为 SFT 结论：

1. interactive-002 在合法 `validate_plan` 调用之前附带解释。原转换器拒绝整个输出，
   而项目原有 native assistant 契约允许 `content` 与 `tool_calls` 同时存在。
   这是适配器缺陷，不足以证明模型不会规划。
2. interactive-008 已产生一次写入并遇到注入的响应丢失，最后直接输出
   `{"outcome":"applied"}`，没有调用 `finish`。该终止错误仍须记录为任务失败，
   不允许自动补成工具调用。
3. 首轮前后非量化层精度设置也不完全相同；它是兼容性检查，不是严格的效果对照。

修订版保留解释文字为 assistant `content`，严格解析 `<tool_call>` 中的 JSON，
拒绝无标签 JSON、重复键、NaN、不完整标签和超限批次。没有自动补动作、改参数或
放宽环境审批。上下文超限在 GPU 生成前拦截，记已知零生成用量；该案例失败，后续
案例继续执行，不误触发 hosted API 的未知账单中止逻辑。

随后按同一修订版、同一精度准备、greedy 解码、4,096 上下文和 512 输出上限，
分别运行未适配模型和 20-step adapter 的全部 14 个开发场景。原始试跑与这两组结果
分开保存，不把解析修复和训练收益混为一谈。

修订接口后的完整结果如下，两组均为同一 14 个公开开发场景：

| 指标 | 未做项目适配 | 20-step adapter |
| --- | --- | --- |
| 任务通过 | 6/14 | 10/14 |
| 参与 smoke 训练的 8 个场景 | 4/8 | 8/8 |
| 未参与 smoke 训练的 6 个公开开发场景 | 2/6 | 2/6 |
| 模型生成次数 | 87 | 118 |
| 输出 tokens | 9,208 | 4,979 |
| 单次生成 P50 / P95 | 3.80s / 18.26s | 2.83s / 8.68s |
| 被拦截的写入尝试 | 0 | 3 |
| unnecessary_clarification 错误 | 1 | 24 |

配对结果：两者都通过 5 个，只有 adapter 通过 5 个，只有未适配模型通过 1 个，
都失败 3 个。**净增的通过数全部来自参与训练的场景；其余 6 个公开开发场景的
总通过数没有增加。**这些也不是预先冻结的未见测试，因此不能据此宣称泛化提升。
adapter 单次回复变短，但工具调用总数增加，整体效率不能只看单次响应延迟。

adapter 的四个失败明确决定下一轮优先级：

| 场景 | 实际失败 | 下一轮覆盖重点 |
| --- | --- | --- |
| 005 | 对已知 equipment 再澄清，然后错误地结束为 infeasible；该例从通过变为失败 | 有效约束组合、无需澄清的判断、可行性标签 |
| 010 | 撤销/过期批准后 3 次 apply 被拦截，其中还改错 proposal ID；最终状态也不对 | 批准撤销、不可重试错误、ID 原样引用、正确 declined 状态 |
| 012 | 对已知字段重复澄清 22 次，耗尽 24 步 | 读取明确偏好、非重试错误后的策略改变、防循环 |
| 014 | apply 意图且仍待批准，却结束为 previewed | awaiting_user 与 previewed 的区分 |

010 的实际写入数是 0：环境拒绝了这些尝试。它证明了执行保护仍有效，同时暴露
模型策略的风险；不能因为最终没有越权写入就把模型的三次错误尝试忽略。

全部 32 条轨迹（原试跑 2+2、修订接口 14+14）可离线回放；审计还交叉核对原始
生成、native 消息、token 计数、报告指标、adapter 哈希以及 20 步确定性采样计数。
审计验证记录自洽，不是第三方硬件执行证明。

## 下一轮实验的约束

先做离线数据与评测工作，再开 GPU：

1. 审查本轮完整失败轨迹，区分接口、终止、审批、约束规划、超时恢复、上下文上限。
   已经用来修代码的 14 个场景永久保留为公开开发回归集。
2. 新建按能力类别分层的场景 family 与 persona，训练/开发/测试组互斥。先冻结
   held-out 定义与输入哈希，再生成训练轨迹；不能把原 14 个场景改名当成测试集。
3. 建立独立标签检查和成功/恢复轨迹审计。正式比较预注册为同一未适配模型、
   successful-only SFT、successful+recovery SFT，匹配**监督 token 预算**，保持接口、
   解码和调用预算相同。DPO 暂不开始。
4. 用生成后的实际序列与目标 token 总数估算训练时长，复测最长序列显存，再锁定
   运行时间。当前证据支持继续使用 4090；没有升级 A800 的证据。
5. 下一次 GPU 窗口建议先限定 2 小时，按当前单价计算 GPU ¥4.36，连同缓冲建议总额
   ¥10。这是待下一批数据完成后复核的预算，不是已经启动或预订的新实验。
   该窗口用于小批量验证，不承诺覆盖完整三组正式评测。自回归 Agent 回放比本次
   20 步训练更耗时；完整矩阵须分别按轨迹长度、每例延迟、案例数及重复次数计费。
