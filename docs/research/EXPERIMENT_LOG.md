## 2026-09-29：固定状态诊断窗口

### 做了什么

使用已通过 CI 的 commit `992ac9ac6df34ea2364f3e58ecd6358a2f6f6052`，在新开的
4090 实例上恢复已有环境、模型缓存和两份 recovery-v2 final adapter。代码通过
SHA 校验的 Git bundle 部署到新的 detached checkout，服务端 push 禁用；旧实验
和权重保留。先复核环境、冻结数据与测试，再运行 19 状态 × 2 adapter。
结果发布、复盘工具与学习记录：[PR #18](https://github.com/Townzc/liftcut-tracker/pull/18)。

### 为什么这样做

本轮使用上一轮已经保存的诊断设计，模型结果尚未用于修改以下比较：

- 确认组：同一个合法预览之后，比较直接接手、多一次读取、被拦截写入三种历史。
  同组的业务状态必须相同；另有一个真实批准的正对照。
- 记忆组：让原始 context、旧确认记忆、当前有效记忆、无效高 revision 分别对应
  不同器械值，再改变记录顺序和是否经过真实时长澄清。
- 每条最多 3 次真实请求，评分第一项有任务含义的动作；模型发出的合法只读 batch
  全部执行。这样避免无限重试，也避免只保留一个有利动作。

这回答“在已取得必要信息的状态下如何决定”，不替代完整任务成功率。没有新的
训练、seed 或保留测试。首个器械选择与某条记录相同，也不证明内部注意力来源。

### 结果与执行状态

已完成。C/R 确认状态分别 5/10、6/10，记忆状态 2/9、1/9；44 次真实生成，
无自主越权写入、格式失败、截断或上下文拒绝。服务端 240 项测试通过；21 个归档
文件在本地核验，38 条诊断全部重放通过后上传 acknowledgment。随后 SSH/SFTP
连接关闭，后续重连超时；未独立核实平台电源和账单。从容器启动代理至后续连接
检查的计算费代理约 ¥0.42，规划预留 ¥3；未知存储费单列。

**观察：** 两组在额外 get_context 之后都执行 get_memories→search，包含已经拒绝
或撤销的状态。R 的 pending 改善仅在被拦截写入之后出现。八个主要记忆状态中，
C 七次选原始 context；R 六次选旧确认记忆、两次选无效高 revision。

**事后追加分析：** 对照冻结 SHA 读取原 v2 训练决策池，发现每个池的 64 个
get_context 后目标全部是 get_memories，没有重读后应 finish 的目标。八个训练
记忆 fixture 只覆盖“有效首位+未确认”和“有效末位+过期”，另两个交叉组合为零，
且原始 context、旧记忆和无效记忆值总相同。这些数量是决策池/fixture 覆盖，
不是训练加权频次，不能冒充运行前已经验证的原因。

**解释与局限：** 结果与依赖工具顺序及数据相关性的假设一致，但没有证明模型
内部机制。首个决定不等于完整任务结局，同值选择不等于内部因果来源。此次结果
不能证明 R 整体优于 C，也不改写 recovery-v2 未达门槛的结论。

详细表格、原始证据和费用观察：[本轮结果](2026-09-29-state-diagnostic-results.md)。
本地分析与发布工具完成后，248 项 CPU 测试通过；公开证据的哈希清单、38 条回放
及训练覆盖报告均重新核验通过。它们属于结果审计，不增加模型实验样本。

### 下一步与判断条件

在 CPU 上准备 [2×2 状态覆盖训练设计](2026-09-29-state-coverage-next-plan.md)，分别
操纵预览后读取历史与记忆排列覆盖，四组匹配正确目标与监督 token。共同改变的
基础数据不能归因于其中某个因素。设计和 token/预算门槛尚待实现，通过后再通知
开服务器；不立即追加训练、seed 或保留测试。

### 本轮需要能独立解释的问题

1. 为什么增加一次 get_context 只能控制部分历史差异，不能完全匹配错误消息？

4. 为什么正确引用一条 memory ID，仍可能做出错误计划？
5. 为什么本轮复用 adapter，不重新训练或更换更大模型？
