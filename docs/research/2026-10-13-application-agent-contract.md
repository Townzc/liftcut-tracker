# 研究Agent接入应用：单条完整流程契约

本页是根据实际代码审查得到的接入任务清单，尚未实现新API、数据库迁移或在线模型服务。本夜没有修改真实用户数据。目标是把已经研究过的Agent能力落到一个可验证的使用流程，界面范围只为解释、批准和检查Agent行为服务。

## 当前实际代码与缺口

[结构化生成](../../src/services/ai/generate-training-plan.ts)调用一次JSON生成服务，随后做归一化与schema检查。[保存路由](../../src/app/api/ai/save-training-plan/route.ts)验证登录用户，接收前端plan后调用持久化；generation_id用于可选历史更新。这个已有手工保存流程不能直接作为Agent的`apply_plan`：它没有研究环境的提案ID、上下文版本和原动作幂等契约。

研究[PlanEnvironment](../../research/liftcut-agent/src/liftcut_agent/environment.py)已经有外部用户事件、批准精确提案与上下文、撤销后禁止执行和同键重放。它是内存模拟器，不是现有业务存储的访问控制或事务保证。现有8工具不能只换一组API地址就视作完成接入。

## 最小纵向范围

只做“用户请求调整训练计划→生成可检查预览→明确批准当前版本→幂等保存”这一条流程。暂不扩到营养、多模态、多Agent或在线RL。研究模型可以先通过独立推理服务接入；服务不可用时显示运行失败或保留待续状态，不冒充已执行。

| 边界 | 新契约 | 必须验证的行为 |
| --- | --- | --- |
| 会话 | 服务器生成run_id、绑定已验证用户、候选版本、读取权限、累计预算 | 客户端不能指定另一个用户或修改系统候选 |
| 状态与记忆读取 | 数据适配为公开工具schema；保留更新时间、有效期、确认状态和来源 | 不把完整业务对象、评分答案或其它用户数据交给模型 |
| 澄清 | Agent只能请求字段；只有真实用户事件可提供确认/修正 | 没有回复时暂停；不由模型代答 |
| 来源与ID视图 | 复用固定D投影，逐调用保存原输入、实际模型输入及逆映射结果 | 未知新别名拒绝；批准/提案/重试键不参与证据改名 |
| 提案 | 服务器保存不可变proposal版本、内容哈希与context_revision | 用户改约束后旧预览明确过期 |
| 批准 | 用户请求绑定run、proposal版本、内容哈希、context_revision；只记录外部事件 | Agent文本里的“批准”没有权限；批准旧版本被拒绝 |
| 执行 | 原子核对用户、当前批准、提案和上下文，使用user/run/proposal/幂等键绑定的写入回执 | 双击、网络丢回包、重试只写一次；同键不同内容冲突 |
| 观察 | 记录原生工具输出、环境结果、批准事件、状态转移、token和停止原因 | 断线后能用同一run回看，原始事件不被模型摘要覆盖 |

执行状态建议限定为`reading → awaiting_clarification / planning → awaiting_approval → applying → applied`，另有`declined / failed / budget_exhausted`终态。恢复前先读取真实服务器状态，不能从客户端“重发开始”创建第二条隐蔽执行。最终字段命名和持久化实现需独立代码审查，本页不宣称这些状态已在线存在。

## 验收脚本

1. 正常生成预览，不批准，数据库写入数仍为0；批准当前版本后写入1次并返回原提案回执。
2. 预览后修正时间或器械，旧批准失效；必须读取新版本并重新预览，不能执行旧计划。
3. 先批准后撤销，模型即使再次调用apply也不能提交；记录“尝试”和“已提交”两个计数。
4. 应用已提交但回包丢失，重试相同动作和键返回原回执；更换内容但沿用键被拒绝。
5. 两个并发批准/执行请求只产生一次提交；跨用户读取、批准、回执查询均拒绝。
6. 模型产生未知证据ID、错误schema、预算耗尽或推理服务断连，保存失败轨迹，没有业务写入。

先在本地合成开发fixture和模拟存储上把这些脚本跑通，再接真实存储并做事务/并发测试，最后接真实模型，避免把三类故障混在一起。页面验收还应让用户看清“当前提案”“等待你的批准”“已经写入的版本”，并能展开来源及关键工具步骤。

学习检查点：在纸上画出一次丢回包重试，指出批准、幂等键和结果回执各由谁创建、谁有权修改，说明为何模型输出的成功文字不能替代已提交状态。
